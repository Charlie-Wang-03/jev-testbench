# Agentic Engineering 与认知负债

[English](AGENTIC_ENGINEERING_AND_COGNITIVE_DEBT.md) | **简体中文**

**状态说明** 本页记录项目过程，不作为 Jev 证据。本页没有任何测量，也不受证据冻结或
[`BLOG_CLAIM_CONTRACT.md`](evidence/v0.1.0/BLOG_CLAIM_CONTRACT.md) 约束。测量在 canonical 日志里，
谈论这些测量的规则在 claim contract 里；本页是另一类对象，并且是刻意分开存放的。

有两个问题在这里很容易被混在一起，因此全文一直把它们分开。

- **对象层**。TypeSafe Jev 在这台机器上、在我们的输入上做了什么。这是证据。
- **元层**。搭建这个实验台这件事，对维护者理解它造成了什么。这是本页。

## 1. 在这里，「Agentic Engineering」指什么

这里的「Agentic Engineering」只描述本仓库采用的一种协作方式，不给整个行业下定义。写得更宽泛，就会声称一个项目
支撑不起的东西。

这种协作里有四部分。

```
人类 owner
+
ChatGPT            规划与复核
+
Claude Code        实现与执行
+
Git、测试、canonical 证据
```

第四部分负责把协作落到**比对话活得更久的产物**上。包括 commit、测试套件、一个
只追加的日志（无论调用成功还是抛异常都会写入记录）、审计文档，以及每个阶段一份书面的 work order。在这里，
一个没有落到 commit 上的建议等于没发生过；一条追不到日志记录的结论不会在这里被写出来。

定义到此为止。它没有说这种方式是否高效、是否明智、是否可以在别处复现，本项目也没有测量过其中任何一项。

## 2. 谁做了什么

**这份归属是 owner 的声明。** 它不能从仓库里推导出来，也无法由仓库独立验证。Git 记录*什么时候哪些
行变了*，却记录不了*谁决定了它们应该变*。下面这张表是关于过程的证词。release notes 也会陈述过程，区别在于
测量可以被核对，而这份归属不能。

分工一律用**「主要」**来表述。每一行代码、每一句话都无法被精确归属，而声称能够精确归属，在两个方向上
都是不真实的。

| 参与者 | 主要负责 |
|---|---|
| **人类 owner** | 提出最初问题；决定项目目标；决定每个阶段的方向；批准与否决关键步骤；处理只有 owner 才能做的决定，包括 license、opaque ID 的发布、实验退役、文章风格、项目更名；承担最终署名与发布责任。 |
| **ChatGPT** | 问题拆解；阶段规划；证据复核；实验设计建议；验收标准；下一阶段的 work order；编辑与写作监督。 |
| **Claude Code** | 进入仓库实施；代码修改；测试；实际执行 Jev 实验；修复；文档维护；文章草稿与结构性改写。 |

这张表只说明本项目如何分工。ChatGPT 和 Claude Code 承担不同工作，不能据此视为可互换。方向、否决和最终署名始终由
人类 owner 保留。

## 3. 认知负债，这里只是一个工作概念

**认知负债**在这里是一个*工作概念*。它不是本项目提出的学术术语，本项目也不主张任何优先权。

这里暂时这样定义。

> 项目中已经实现、自动化和记录下来的复杂度，
> 与 owner 能够独立解释、验证和修改这些内容的能力之间的差额。

如果一定要压成一行，只能写成下面这个非正式近似。

```
认知负债  ≈  已实现的项目复杂度  −  已被独立理解的项目复杂度
```

**这不是一个可测量的量。** 它没有单位，没有量具，在本仓库里也没有任何取值。上面那行只是用来指一个形状，
不是公式。它无法从 canonical 日志、从代码行数、或者从已经过了几个阶段算出来，[`results/`](../results/usage.jsonl)
里的任何东西都与它无关。

具体到本项目，这个差额会表现成几种同时成立的状态。东西是**真的、在跑的**，但 owner 未必随时能完整
解释它。一个模块可以说出高层行为，却无法凭记忆重建；一个冻结的 release，验证路径可以跑，却推导不出来；
一份文档因为流程要求而存在，却已经没有人在读它。

认知负债不是代码缺陷，也不等于未完成的任务。未完成的任务是还没做的工作。认知负债是**已经做完**的工作，
只是做成了它的 owner 无法独立重新推导的形式。

## 4. 外部机制不是理解

这是最重要的一条限制，本页其余部分的存在就是为了把它说清楚。

本仓库用了下面这些外部机制。

| 机制 | 它是什么 |
|---|---|
| [Canonical 日志](../results/usage.jsonl) | 只追加的记录，每次真实 API 调用一条，无论成功还是抛异常都由 recorder 写入。 |
| [预注册](experiments/P3_BOUNDARY_LOCUS_PREREGISTRATION.md) | P3 的设计、阈值和停止规则，在第一个请求发出之前冻结。 |
| [Claim audit](blog/jev-as-probabilistic-decision-primitive.CLAIM_AUDIT.md) | 文章中每一条实质结论，对应到允许它的 claim contract 类别。 |
| [Errata](ERRATA.md) | 事后发现的缺陷，公开记录并跟踪，而不是悄悄修掉。 |
| [证据冻结](evidence/v0.1.0/PUBLIC_EVIDENCE_FREEZE.md) | 版本 `v0.1.0`、它的 manifest，以及一个离线重新哈希整个集合的 verifier。 |
| [测试](../tests/) | 一个封锁 socket 的离线套件，因此测试不可能悄悄打到真实 API。 |

这些机制确实有用。日志会**保存事实**，不会因为结果难看而软化。claim contract 会**约束叙事**，两种语言都拒绝
数据支撑不了的措辞。它们还会**支撑事后重建**，某个人，包括一年后的 owner 自己，可以顺着这些记录走回去。

它们**不会**自动变成人的理解。

这个区别正是重点。一个通过的测试是关于产物的事实，不是关于交付它的人的事实。一份冻结的 manifest 证明一组
字节没有移动过；它不证明还有谁活着能重建那组字节。一份 claim audit 检查的是文章被允许断言什么；它不检查
作者能不能在没有它的情况下、当着人把这条断言讲下来。

这些机制让「说出假话」**更难**，却不会替维护者生成理解。两种能力需要分开看。拥有前者时，人很容易误以为自己也
拥有后者，认知负债就在这里累积。

## 5. 本页不主张什么

- 本页不提供 Jev 结论。它在 [`BLOG_CLAIM_CONTRACT.md`](evidence/v0.1.0/BLOG_CLAIM_CONTRACT.md) 之外，
  contract 的 `SAFE_TO_STATE` 与 `SAFE_WITH_SCOPE` 类别不约束它。过程性主张由 owner 声明与本记录负责；
  证据性主张由 contract 与冻结负责。
- 本页也不提供测量。这里没有任何数字来自 canonical 日志，任何内容都不应被引用为关于 Jev、TypeSafe，
  或 AI 辅助开发的普适发现。
- 本页不评价这套做法。这是一个项目的记录，样本量为 1。这种方式是否值它的成本，本文档不作判断。
- 本页没有把「认知负债」发展成理论或量化框架。它在这里只是一个项目级工作概念。

**把两个域分开，是为了守住 evidence layer 的边界。** 如果过程性陈述进入证据层，这一层的保证就会开始为它从未被设计去检查的
主张背书，冻结的 verifier 也会为一堆它读不懂的文字作证。
