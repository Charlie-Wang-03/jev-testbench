# 我跑了 54 次调用，删掉了七个关于 Jev 的故事

[English](jev-as-probabilistic-decision-primitive.md) | **简体中文**

事情是这样的。

我第一次看到 Jev 的时候，让我好奇的不是它又拿了什么 benchmark。

是它压根不想跟我聊天。

不给我一段文字，不给我解释，直接扔一个带类型的概率答案过来。你问它一个问题，它回你一个 label，一张概率表，完了。

我当时冒出来的问题特别朴素。如果模型天生就是拿来做 classify、route、score、gate 的，那 Agent 会不会真的好写一点？

所以我真去跑了。

54 次。

---

先说一分钟背景，不然下面看不懂。

一次 Jev 调用的形状是这样。你给它一份 `state`，再给它一组带类型的问题，它回你一组带类型的答案。同一个请求里的所有问题看到的是同一份 state，彼此独立求值，一个问题看不见另一个问题的答案。这一点后面用得上。

问题只有三种。

Choice 最直观，给几个选项，它返回赢家和整张概率表，表里的数加起来是 1。

Score 稍微绕一点。它不是在 1、2、3 里挑一个，值可以落在两个档位中间，官方定义是等级编号的概率加权平均，另外附一个 confidence。

Noul 最简单，只有一个数，P(yes)。

这里有两件事我一开始差点搞混。

第一，答案里没有自由文本。我跑完的 42 条核心记录里，45 个 Noul 答案一个都没有 confidence 字段，而每一个 Choice 和 Score 答案都有。这个 45 / 45 我一开始写错过，后面讲。

第二，probability 和 confidence 不是一回事。probability 是选项上的分布，confidence 按官方说法是从返回的分布算出来的一个统计量。它们在同一个答案里并排返回，是两个不同的数。我第一次调用就撞上了，赢的那个选项概率 0.45，同一个答案的 confidence 是 0.26。

如果这一段只能带走一句话，那就是，类型化输出解决的是 schema 的问题，不是语义的问题。格式全对，不代表它对，更不代表它该被执行。

TypeSafe 自己的文档在这点上写得挺直白。已知局限那一页把字面阅读、弱数值表示、日期比较、指代、大 state 一条条列了出来，并且明确说控制流应该留在代码里，模型只做窄决策。这不是我发现的，是厂商公开写的。

---

产品文档描述的是产品应该怎么工作。这两件事之间的差距，才是工程上真正要付代价的地方。

但「我觉得它有时候不太行」这种印象，本身不能拿来做事。

所以我先建了一个测量台，叫 `jev-test`。它的目标不是给 Jev 打分，也不是做排行榜。它只有一个目标，让每一个结论都能被追到一条日志记录上。

第一轮跑完以后我马上发现一个麻烦。

如果我现在开始写文章，我其实可以非常轻松地把它写得很好看。

挑两个数字最大的效应，配一张图，说 Jev 在某个地方比官方文档说的还厉害，或者还差。没人会去查。

所以我反过来先给自己加了一堆限制。

最上面一条是，厂商说的任何数字，都是关于他们的 workload 的主张，不是关于这台机器、这个账号、我这些输入的测量。只有 `results/usage.jsonl` 里由真实调用写出来的一行，才算本地测量。写的时候必须说清楚每一句报的是哪一种。

然后是日志。一次真实调用产生且只产生一条记录，成功也好，抛异常也好。失败的调用也是数据，不删、不重排、不修一下再写。这次用到的两个日志，SHA-256 分别在 `38e67630…` 和 `17f36f75…`，从头到尾一个字节都没变过。

模型身份也得记。我调用时写的是别名 `jev-latest`，但 42 条记录实际返回的都是 `jev-1.13.0`。别名会漂移，只有响应能说明到底是谁回答的，所以两个字段都记。

token 数就用 API 返回的 `usage` 值，从不估算。成本和延迟是我自己推的，明确标成本地推导，不当事测量结果。

还有一条，派生产物不能漂移。`results/` 下面除了两个 canonical 日志之外的所有文件，都是从日志重新生成的。CI 会重新生成一遍再和提交的版本比对，不一致就直接失败。一个派生报告永远不能变成第二个真相来源。

最要命的那条是，先预注册，再调用。这个后面细说。

做到后面我意识到一件事。这个仓库想评估的其实不只是 Jev，它同时在评估我自己有没有资格从一次模型输出推出一个更大的结论。

而这个问题的答案，大多数时候是没有。

顺便说一下成本。这 54 次调用按本地估算花了大概 0.001 美元，千分之一美元这个量级。这是本地估算不是账单，TypeSafe Console 的计费才是权威。写这个只是想说明，独立验证一个模型行为的门槛，比很多人想象的低。

---

好，回到实验。

第一轮登记了 10 个实验，全部跑完，42 条核心记录。我本来想按登记顺序讲，但那样很难看，所以按当时的兴奋程度讲。

第一个让我觉得有点东西的是批处理。

把共享同一份 state 的五个问题放进一次请求，两轮顺序平衡的循环合计吃掉 816 输入 token。把同样五个问题拆成五次独立请求，同样两轮合计吃掉 3,480。

3,480 除以 816，4.2647 倍。省掉 76.55% 的输入 token。

而且两个臂之间，10 / 10 个选中值完全一样，最大绝对差是 0.0。

漂亮。

三个数字摆在这，任何一个想写点东西的人都会停一下。

但边界必须跟数字一起说。这是一份 payload 上的数字，五个问题全读同一份 state，而这恰恰是这个节省成立的前提。它是两个顺序平衡循环、一次会话里测出来的，不是平均值，更不是分布。它不是通用倍率。

最关键的是，它不能跟厂商公布的倍率放在一起比。TypeSafe 在 `primitives.md` 里写的是 13 个问题 batch 到一次调用比 13 次分开调用便宜 11.5 倍、快 9.6 倍，在并行问题那一页写的是 12.2 倍和 10.0 倍。这是两种不同的 workload，问题数不同、payload 不同、分母不同、会话不同。把「官方 12.2 倍」和「本地 4.26 倍」并排写成「官方 vs 实际」，是范畴错误。

诚实的说法只有一句。在这个 payload 上，本地测量复现了官方描述的共享 state 摊销机制。

而且是预期之中的机制。公开的第三方测量在同一模式上走得更远，他们变化了 batch size，还给出了准确率随 batch size 变化的曲线。我这个实验从头到尾只用了一份固定 payload。

所以这是复现，不是发现。

第一个故事没了。

---

第二个我到现在还觉得挺有意思。

我把一份逐字节相同的 512-token 请求发了五次。胜出的 Choice 标签 5 / 5 都没有变。

但在那个不动的标签底下，分布是在动的。前两名间距最多移动了 0.07，Score 落在 1.58 到 1.63 之间，confidence 在 0.24 到 0.30 之间，还有一次出现了前两名之间的精确并列。

标签稳如泰山，底下的水一直在晃。

我当时是真的觉得这条挺有意思。

然后我去翻官方 cookbook，找到了它。TypeSafe 自己的文档报告了 8 个问题里有 2 个出现标签翻转，还给了逐标签的概率标准差，均值 0.0098，单标签最大 0.0515，并且明确写了一句，当两个标签接近时，很小的变化仍然可以翻转 top label。

措辞不一样，但我说的事情已经在它里面了。

更决定性的是公开材料。有一份公开的 chaos test 报告，他们把逐字节完全相同的请求发给 Jev 五次，拿到的是 0.03、0.03、0.03、0.04、0.04，并且在约 1,490 次捕获调用上测了 jitter floor。

我以为是「我们独有」的那个设计，用逐字节相同的请求做重复，别人已经做过，样本量比我大，统计比我好。

有意思的观察不等于新的发现。这两件事之间隔着的，恰恰是有没有人先做过。

第二个故事也没了。

---

第三个最短，也最适合拿来说明问题。

我在 `04_confidence` 里特意设计了一个模糊用例。它返回的 intent 是 `other`，confidence 是 0.61，正好越过我在代码里设的 0.60 门槛，于是被判成 accept。

这么写出来，听起来像模型在一个很微妙的边界上做了判断。

不是。

0.60 是我自己在 `experiments.py` 里写下的常量，代码注释里就标了它是 demonstration threshold，没校准过，没在任何数据上调过，不声称最优。TypeSafe 的文档自己也在两个不同页面上对同一个示例用了 0.5 和 0.6 两个门槛，并且明确说门槛必须按领域调。

而且那次返回的分布根本不接近。0.74 对 0.26，间距 0.48。那个「模糊」是我 state 设计的属性，不是返回分布的属性。官方的 k=3 近似式 `(3 × 0.74 − 1) / 2` 把 0.61 精确地重算了出来。它就是一个算术结果。

0.61 大于等于 0.60，是我们自己的策略算术，不是 Jev 的发现。移动那个常量，结论就变，而且一次模型调用都不需要发生。

第三个故事，没了。

---

第四个是我当时最想看结果的一个，也是最后一个被删的。

我让模型把请求路由到一个事先冻结的函数注册表。结果是，模型 4 / 4 次匹配上预期的函数，4 / 4 次匹配上预期的参数。

然后 4 / 4 次全部被我的策略拦下来送到 `human_review`，handler 一次都没进去。

这个结果太容易写成「模型不敢执行」了。

不是。

四个拦截全部能追溯到我自己的 `routing.py`。路由置信度分别是 0.76、0.58、0.72、1.0，我把 floor 设在 0.8，前三个只是因为落在这条线下面才被拦。第四个置信度是 1.0，是被 `needs_human_review` 的 0.94 相对 0.5 的门槛拦下的。

紧挨着那个常量的位置，我自己写了一行注释，`nothing in the docs says 0.8 is the right line`。

是 router 在按我的指令拒绝执行，不是 Jev 产出了不可用的 confidence。

第四个故事，也没了。

这几段连起来看，最容易写进博客的故事，恰恰是最需要被删掉的。七个候选里，效应最大的两个，批处理和第四个，死得最彻底，两次都是「别人公开做过」决定了它们的命运，不是我的数据不够好。

没有任何一个候选因为不好看被杀掉，也没有任何一个因为好看被留下来。

---

七个候选跑完对抗性审查，只剩一个。

它活下来的理由不是效应大，恰恰是它有一个明确的、可以证伪的未知。

事情来自 `07_instruction_precision`。我在一份逐字节相同的 82 字节 state 上，改了决策边界的写法。模糊的边界下，一个 Noul 返回 0.75。明确的边界下，返回 0.20。

同一份 state 字节，0 到 1 的概率上，差了 0.55。

这个效应很大。大到我看到它的第一反应，是想赶紧写点什么。

但它有两个问题。

第一，0.75 和 0.20 都不是 ground truth。两个臂都无所谓正确，它们只是两个不同的数。

第二，也是关键的那个。

我的两个臂，同时改了 instructions 和 criteria。

所以这个实验支撑不了任何一句这样的话。不能说 Jev 更看重 criteria。也不能说光改 prompt 措辞就造成了 0.55。

能说的只有一句，在这份 payload 上，两个字段一起从模糊改到明确，Noul 移动了 0.55。

而这件事恰好撞上一个官方文档没有回答的问题。TypeSafe 的已知局限页把「字面阅读」列成失效模式第一条，给的补救办法是在 instructions 里说明确的条件，把边界情况写进 criteria。官方还给了一句，把 criteria 当作 instructions 的延伸。

但它给的是一个打包的建议，从来没拆开过。

那个边界，到底是 instructions 在承载，还是 criteria 在承载？

官方没拆。我自己的数据没拆，两个字段一起改的。公开材料里我也没找到带控制变量的归因实验。

问题来了。

到底是谁动的？

这就是唯一一个通过审查、又值得花几个调用去问的问题。

顺便说一句，这个问题的公开新颖性检查返回的是 `PUBLIC_NOVELTY_UNRESOLVED`。我把它记成「未解决」，而不是「没有人做过」。这两者不是一回事。

---

到这一步，我知道自己要小心了。

因为我手上有一个 0.55 的大效应，一个听起来很漂亮的问题，和一整套可以让我顺手把它讲圆的自由。

所以我在发第一个请求之前，把设计、顺序、统计方法和每一条阈值全写下来，提交了。

设计是一个 2×2，把两个字段交叉开。

| 臂 | instructions | criteria |
|---|---|---|
| `N` | 模糊 | 模糊 |
| `I` | 明确 | 模糊 |
| `C` | 模糊 | 明确 |
| `B` | 明确 | 明确 |

每个臂重复 3 次。

一共 12 次调用。

12 次。一条都不许多。

这是一个写死在预注册里的硬上限，不允许重试循环，不允许轮询，不允许「再补几次看看」。

顺序也提前固定了，`N1 → I1 → C1 → B1 → B2 → C2 → I2 → N2 → C3 → N3 → B3 → I3`，两端和中间都做了平衡。

预注册里还有一条设计风险，我觉得它比阈值本身更重要。`I` 和 `C` 两个臂必须陈述同一个边界，只在写在哪里上不同。如果哪个臂让 instructions 和 criteria 互相矛盾，它就触发了官方记录的另一条失效模式，那个臂就是协议违规，不是数据点。

`N` 和 `B` 这两个端点臂，是原来 `07` 实验两个臂的三次重复版本。它们的作用是诊断，检查原来的效应这次还在不在。它们和所有阈值一样，在第一个请求发出之前就冻结了。

所以事后没有人能拿它们去调阈值。

决定性的那条 KILL 条件是这么写的。

```
K1:  |I_med − C_med| < 0.1   →  归因失败
```

---

12 次调用全部成功。

原始值我全部列出来，中位数是对它们的概括，不是它们的替代品。

| 臂 | Noul 原始值 | 中位数 | 极差 |
|---|---|---:|---:|
| `N`（都模糊） | 0.77, 0.76, 0.75 | 0.76 | 0.02 |
| `I`（只改 instructions） | 0.31, 0.33, 0.29 | **0.31** | 0.04 |
| `C`（只改 criteria） | 0.37, 0.36, 0.33 | **0.36** | 0.04 |
| `B`（都明确） | 0.20, 0.21, 0.20 | 0.20 | 0.01 |

端点复现是成功的。原来 `07` 观察到 0.75 到 0.20，移动 0.55，这次跑出来 `N` 中位数 0.76，`B` 中位数 0.20，间距 0.56。每个臂 3 次重复，同一份 payload。次序保住了，量级也保住了。

看到这里，很容易产生一个冲动。

`I` 比 `C` 低。

是不是 instructions 更重要？

不行。

因为我在看数据之前，已经写了一条 K1。

真正发生的事情在两个单字段臂上，它们都朝着明确基线移动了大部分距离。`I` 中位数 0.31，比 `N` 的 0.76 低 0.45，相当于这次 0.56 端点间距的 80.4%。`C` 中位数 0.36，低 0.40，相当于 71.4%。

而两个单字段臂之间，只差 0.05。

```
|I − C| = 0.05
threshold = 0.10
```

0.05 小于 0.10，K1 触发。

按照预注册的规则，结论是，在这个设计和样本量下，原来的效应无法被归因到 instructions 或 criteria 中的任何一个字段。

```
P3_KILL_NO_SINGLE_FIELD_ATTRIBUTION
```

关于那两个百分比，80.4% 和 71.4%，必须说清楚。它们是我对上面几个中位数做的描述性算术，不是决策规则的一部分。没有任何阈值是从它们推出来的，把它们完全忽略掉，判定结果一个字都不会变。

---

我不是第一次做实验。但先给自己挖好一个坑，再自己跳进去，这是第一次。

这次 P3 拿到的不是「没做出来」，是一个真实的负结果。

它不是我实验失败。原来的大效应被复现了，0.55 那次移动，这次以 0.56 的间距重新出现，端点次序一致。失败的是归因。这个设计说不清效应来自哪个字段。

效应很大 ≠ 原因已确定。

看到 0.55，最自然的冲动是马上去写「Jev 更看重 X」。但一个把两个变量一起改掉的实验，无论效应多大，都答不了这个问题。要回答它，你需要的不是更多的调用，而是一个能把变量拆开的设计。而且这个设计必须在看到数据之前就定好，否则你会忍不住一直调整到它能说出你想听的话。

也不能把 null result 偷偷翻译成一句更好听的话。

不能说「Jev 同时看重 instructions 和 criteria」。这个设计区分不了「两个字段都在起作用」和「混合具体度的构造物在起作用」，这是两回事。

也不能说「criteria 才是关键」。数据说的恰恰相反，如果非要说偏好，`I` 臂动得还更多一点。

还有两条限制是承重的，必须跟着结论一起走。

`FIELD_ALIGNMENT_CAVEAT`。交叉的两个臂，是一个更宽的字段加一个更窄的字段，不是两个独立变化的定义。所以这个结果说的是这个混合具体度构造的性质，不是 Jev 到底把决策边界存在哪里。

n = 3。三个重复能支撑一个中位数和一个极差，支撑不了任何区间估计。所以这里没有报告任何置信区间，不是我不想报告，是这个设计支撑不了。

结论就是它字面的意思，一个字都没多。在这份 payload、这个样本量、这个设计下，效应无法归因到单一字段。

---

然后又出了一件挺尴尬的事。

实验没坏。

分析器坏了。

预注册里，GO-1 和 GO-2 是两个独立的条件。我在分析器里把它们写成了一个合并的判断，结果 `(GO-1 PASS, GO-2 FAIL)` 这一对在代码里根本无法被表示。而这份数据上，预注册规则算出来的恰好就是这一对。两个单字段臂都越过了 GO-1 的线，`I_med = 0.31`、`C_med = 0.36`，线是 0.475，但没有任何一种指派能让对方留在 GO-2 的模糊基线带里。有缺陷的分析器把 GO-1 报成了 FAIL，还打印了一句和数据矛盾的话。

我做了这些事。

在有缺陷的分析器冻结点之后、测量被记录的那次提交里，就把缺陷披露了出来，没有等别人发现。修复是一次独立的、后置的提交，没有发出任何调用，也没有重跑任何一次调用，12 条记录在修复前后逐字节相同。没有改动任何阈值、任何规则，预注册文档和冻结时逐字节相同。修复后的分析器，是从没变过的日志重新渲染出来的结果文档。

最关键的检查是这个。原始分析器算出来的主判定，和修正后的完全一样。

为什么？因为 GO-1 单独从来不构成判定。冻结的规则要求的是一条越过 GO-1 的臂，配上一条落在 GO-2 带里的对应臂，而这份数据上不存在这样的配对。K1 在 GO 块之前就被求值，而且它触发了。

所以这个缺陷弄错的是推理过程的显示，不是决定本身。

这件事我没打算写成英雄叙事。它就是一个 bug，我发现了，我记下来了，我没有拿它去重跑一次让自己好看点的实验。

预注册不能保证代码没有 bug。但 provenance 能让 bug 的修复不污染测量历史。

一个后来的人可以自己 `git show` 出修正前的那次渲染，看到缺陷、看到披露、看到修复，然后自己判断这一切是否成立。这就是为什么那次错误的渲染被保留在 Git 历史里，而不是被抹掉。

而且这还不是唯一一次。

P1 审计里有一行写的是，42 / 42 个 Noul 答案不携带 `confidence` 字段。

独立复核的时候发现，正确的数字是 45 / 45。

为什么？

因为我把记录数和答案数混了。42 是记录数，那句话说的是答案数，42 条记录里一共装了 119 个答案。

结论没有任何变化，每一个 Noul 答案确实都没有那个字段。但数字确实错了。

我没有去改 P1 的文本，因为它是历史审计产物。改了它，读者就再也分不清它里面哪些数字被动过。正确的值记在[勘误表](../ERRATA.md)里，P1 原文保持原样。

把这两件事放在一起看，说的是同一件事。这个仓库不在乎它看起来有没有犯过错，它在乎的是，你还能不能自己判断它有没有犯错。

---

跑完这些，我手上剩下三条能迁移到别处的东西。

第一件关于类型化输出。schema 校验通过不等于答案正确。42 / 42 条响应全部通过校验，但这什么都说明不了，没有 ground truth，没有对抗性输入，只有良性 payload 上的格式合规。这是支持类型安全主张最弱的一种证据。

跟它连在一起的是 confidence。官方文档把 calibration 的作用域限定在一组预测上，并明确说 confidence 描述的是模型的答案，不保证答案正确。我本地有一个更扎心的例子。在 `06_composite_scoring` 里，有一个维度在 0 到 3 的评分表上拿了 1.62，而它的 confidence 只有 0.24，这个维度却承载了那份 state 97.4% 的合成风险。算术是对的，confidence 是低的，它们只是两个不同的问题。一个把低 confidence 读成答案错了、把高 confidence 读成答案对了的策略，读的是错的数字。

这里必须明确边界。这个项目既没有验证、也没有证伪 Jev 的 calibration。`04_confidence` 只有两个用例，没有可靠性图，没有 ECE，没有 Brier score，没有独立的 ground-truth 数据集。任何方向都不行。

第二件，语义路由和执行授权要分层。这是这个项目产出的最有用的一条模式，而它来自一次与设计预期相反的运行。模型把活干得很好，4 / 4 匹配正确的函数，4 / 4 匹配正确的参数，然后 Python 侧的策略把每一条都拦了下来，handler 一次都没进去。

系统该怎么写。模型回答这个 state 是什么意思，代码回答我们被允许行动吗。一个把「模型很自信地选了某个路由」当成「可以执行」的系统，恰恰移除了产生这次结果的那一层。

边界也要说清楚。那 4 / 4 是合成用例上的计数，不是准确率。每一个 handler 也都是惰性的，没有写文件、没有发消息、没有真实副作用。在真实答案下，一条被允许的路由是否真的会走到 handler，这个项目从未观察到（`ACTUAL_HANDLER_EXECUTION_UNTESTED`），这条限制是写下来的。

第三件不太像工程建议，更像一条纪律。评估基础设施本身也需要被审计，而这是这个项目最值钱的部分。canonical logs、从日志重新生成的派生产物、离线测试、勘误表、哈希、冻结。所有这些都是为了让「哪些数字被动过」有一个机械的答案，而不是靠作者的信誉。

举个具体的例子。日志里有一个 `retry_count` 字段，它永远是 `null`。原因是 SDK 把重试次数写在被重试的请求上，而记录器读的是响应。所以 `null` 的意思是没有被报告，绝不是没有发生重试。这个字段没有被回填，也没有人拿它做推理，它留在那里只是为了让旧的行仍然可读。真正有效的是 `transport_attempt_count`，一个本地计数的出站 HTTP 尝试次数。它也只能支撑一句话，这次调用没有被观察到重试，不能支撑「这是纯粹的模型推理延迟」。

---

还有一件我做得挺狠的事。

在公开发布之前，我把 5 个已经登记但从未运行的实验全部退休了，而不是为了完整性把它们跑完。

它们当初都是认真设计的，退休是因为站不住。举两个。

`10_state_length` 用不断增长的无关填充文本，装载一份固定的核心证据。它有三个缺陷叠在一起。没有独立的 ground truth，「正确」答案是我自己对一份我自己写的合成 bug 报告的读法。每个长度档只有 1 次调用，split 不开 context rot 和随机波动，而我自己另一个实验已经证明，逐字节相同的 payload 上 Noul 都会动。而且那些填充段落其实只有五句话在按 `index % 5` 循环，「中等」和「更长」两档的区别是同样的五句话重复了几遍，不是无关内容累积了多少。重复和累积是两种不同的操纵，所以这两档根本没有在变化这个实验名称所指的那个变量。

`11_language_pair` 是英文和中文的等价输入。这个退休理由最值得看，因为留下来的诱惑最大。我本人和相当一部分读者是中文使用者，一个中英对照的结果会很好看。

但它有四个独立的问题。两个臂在语义上并不等价，英文 state 说客户想撤销重复扣款，配对的问题却问的是要不要退款，这是两个不同的诉求。语言和措辞被完全混淆，每种语言只有一种写法，所以任何差异都是语言乘措辞。每个臂只有 1 次调用。而且官方文档已经回答了产品层面的问题，它直接写明英语是主要训练语言，其他语言包括 CJK 可以接受但目前准确率较低。

第四条本身就是这个项目的规则在起作用。「这个结果会很受欢迎」是关于读者论证，不是关于设计的论证。一个被混淆的、统计功效不足的、语义还有歧义的设计，不会因为它面向的读者是谁而变得可用。

一个实验已经写完代码了，到底要不要因为 sunk cost 把它跑掉？

我的答案是不要。

不运行一个坏实验，通常比得到一个无法解释的数字要好。退休一个从未运行的设计不会损失任何证据。一个从未运行的设计只是一个意图，而删掉一个意图不是丢掉一个结果。

（顺带一提，这也是为什么这个仓库没有「登记但未运行」这个状态。要么跑，要么退休。）

---

写到这里，得把「这些实验没有证明什么」说清楚。这不是以后再补的问题，是证据结构上不支持。

没有通用准确率。这个测量台里没有任何地方存在 ground truth。「4 / 4」是合成用例上的计数，永远不是比率。

没有验证或证伪 calibration，任何方向都没有。

没有模型延迟 benchmark，也没有任何加速结论。延迟被记录了，但它包着一整段东西，DNS、TCP、TLS、连接池状态、服务端排队、上游负载、本地调度。没有任何一个臂被称作更快。

没有通用的批处理倍率。4.2647 倍是一份 payload 的属性。

没有确定性结论，两个方向都没有。逐字节相同的请求返回了不同形状的分布，但那只是两个 payload 上的少数几次重复，不足以成为判定。

剩下几条顺带说完。没有广义的 hallucination benchmark，这里唯一测量的轴是良性 payload 上的 schema 合规。没有生产安全认证，每一个 handler 都是惰性的。没有关于 instructions 和 criteria 谁更重要的通用结论。没有 NAS 适用性结论。

还有两条不叫 marker 但同样有约束力的。

不做厂商主张的仲裁。当官方数字和本地数字不一样时，这个仓库说的是它们不可通约，而不是官方其实错了，或者本地其实证明了官方。厂商数字是关于他们 workload 的主张。

全部 state 都是合成的。这个仓库里没有真实的个人数据、客户数据或专有数据。

完整的清单在 [`BLOG_CLAIM_CONTRACT.md`](../evidence/v0.1.0/BLOG_CLAIM_CONTRACT.md) 和冻结文档里，我这里只挑最容易误解的说。

---

我确实还想看看 Jev 能不能拿去做 NAS。

但这个仓库现在没有资格回答。

这里没有 NAS 实验、没有 NAS 数据集、没有任何 NAS 测量，而被退休的五个设计里，有可能触及搜索相关行为的那些也从未运行。

下一步如果真要做，得从 NAS 的任务结构出发重新验证，而不是因为已经研究过 Jev，就反过来去找应用场景。

不能因为手上有锤子，就把问题看成钉子。

---

回到开头。

我一开始是想看看 Jev 到底有什么厉害的地方。

54 次调用之后，最好看的几个故事基本都没留下来。

但我现在反而更喜欢这个结果。

因为一个评估仓库真正应该帮你做的，可能从来不是积累故事，而是删掉那些证据撑不住的故事。

后来我才发现，这个仓库真正积累的，不是故事。

是删故事的能力。

发布的时候，这个仓库的诚实总结是这样一行状态。

```
NO_STRONG_JEV_SPECIFIC_NOVEL_FINDING_YET
```

这里没有一条既相对于 TypeSafe 公开材料是新的、又被我自己的数据支持的 Jev 发现。每一个本地大效应，要么是在复述一个官方已经记录的行为，要么是我自己 Python 侧策略的产物。

我认为这是个好结果。一个用来检验发现的仓库收到了否定的检验结果，说明它在做它该做的事，而不是在累积战利品。

说实话，这个项目对我更像一次 model evaluation 和 Agent engineering 的训练，而不是一次 model benchmark。我学到的大部分东西不在 Jev 那一侧。

至少现在，这行字我敢签名字。
