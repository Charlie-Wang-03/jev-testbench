# 把 Jev 当成 Agent 的概率决策原语：54 次调用、一次预注册负结果，以及我学到的模型评估方法

[English](jev-as-probabilistic-decision-primitive.md) | **简体中文**

我用 54 次 API 调用，想搞清楚一件事：**如果模型不生成文本，而是直接返回带类型的概率答案，Agent 的写法会变成什么样。**

先把结论放在最前面，因为它决定了后面每一段该怎么读：**这 54 次调用最终没有留下一个经得住审查、足以称为「强 Jev-specific 新发现」的结论。** 真正留得下来的，是一套可复核的测量方法，和一次必须如实报告的负结果。

这篇文章讲的是这个过程。

---

## 1. 一个 Agent 工程问题

生成式 LLM 很擅长三类事情：generate、explain、transform。但 Agent 的工作流里，大量步骤其实不是生成，而是另一类事情：classify、route、score、branch、gate。

这些步骤的常规写法是：让模型生成一段 JSON，然后在外面解析、校验、失败重试。这条路能走通，但它把「类型正确」变成了一件需要反复防守的事情 —— 模型可能少一个花括号，可能在你以为返回整数的地方返回了字符串，可能在选项之外自己发明一个标签。

于是有一个很自然的问题：

> 如果模型本身就把「输出」定义成一个封闭的、带类型的概率分布，而不是一段需要解析的文本，会发生什么？

TypeSafe 把他们自己的 Jev 模型定位成这类东西。他们的发布博客里有一句话，我觉得是整个产品定位里最凝练的一句：

> Think of Jev as a frontier-intelligence function call: unstructured state in, typed probabilistic decisions out.

需要强调的是，**这是厂商对自己产品的定位，不是我的测量结论。** 这篇文章会反复回到这条区分上，因为它是整个项目最重要的纪律。

为了不靠印象回答上面那个问题，我建了一个测量台。

---

## 2. Jev 是什么，以及它不是什么

按照 TypeSafe 官方文档的描述，一次 Jev 调用的形状大致是：

```
state + 一组带类型的问题 → 一组带类型的概率答案
```

`state` 是被评估的输入，可以是一段字符串、一个 JSON 对象或者一个数组。文档说明，同一个请求里的所有问题看到的是**同一个** state，并且彼此独立地求值 —— 这一点在后面第 5 节会变得很重要。

问题必须来自三种类型之一，答案也相应地只有三种形状：

- **Choice** —— 从给定的选项集合里选一个。返回选中的 label，以及该选项上的完整概率分布，`probabilities` 之和为 1。官方定义 `choice` 就是概率最高的那个选项。
- **Score** —— 沿给定的等级打分。值可以落在两个等级之间，官方定义是「等级编号的概率加权平均」，并附带一个 `confidence`。
- **Noul** —— 只有一个数，P(yes)。因为只有两种结果，单个概率已经描述了整个分布，所以它**不**携带单独的 `confidence` 字段。

这里有两件事值得单独讲清楚，我自己在实验里就差点把它们混掉。

**第一，答案里没有自由文本。** 在我跑完的 42 条核心记录中（一个账号、一个模型版本），**45 个 Noul 答案里有 45 个**都没有 `confidence` 字段，而每一个 Choice / Score 答案都有。这是厂商的文档设计，我只是在本地把它复现了一遍 —— 这个「45 / 45」背后有一个小故事，写在第 11 节。

**第二，`probability` 和 `confidence` 不是一回事。** `probability` 是选项上的分布；`confidence` 按官方文档的说法，是「从返回的分布计算出的一个统计量」。它们在同一个答案里并排返回，是两个不同的数。我在第一次调用（`01_primitives`）里就撞上了这一点：胜出选项的概率是 **0.45**，而同一个答案的 confidence 是 **0.26**。

如果这一节只能带走一句话，那就是：**类型化输出解决的是 schema 的问题，不是语义的问题。** 一个答案格式完全正确，不代表它是对的，也不代表它该被拿去执行。

TypeSafe 自己的文档在这点上说得比很多人以为的清楚：已知局限页逐条列出了字面阅读、弱数值表示、日期比较、指代、大 state 等失效模式，并明确指出控制流应该留在代码里，模型只该做窄决策。这不是我发现的，是厂商公开写的。

## 3. 我没有直接相信文档，而是先建了一个测量台

产品文档描述的是产品应该怎样工作。这两件事之间的差距，正是工程上要付代价的地方。但「我觉得它有时候不太行」这种印象，本身不能拿来做事。

所以我建了 `jev-test`。它的目标不是评测 Jev 好不好，也不是做排行榜 —— 它的目标是让**每一个结论都能被追到一条日志记录上**。

具体做法上有几条硬规则：

**官方主张和本地测量严格分开。** 厂商公布的任何数字，都是关于**他们的** workload 的主张，不是关于这台机器、这个账号、我这些输入的测量。只有 `results/usage.jsonl` 里由真实调用写出的一行，才算本地测量。写东西的时候必须说清楚在某一句里报告的是哪一种。

**日志是只追加的（append-only）。** 一次真实 API 调用产生且只产生一条记录，无论成功还是抛异常。失败的调用也是数据，不会被删掉、不会被重排、不会「修一下再写」。`results/usage.jsonl` 一旦发布就冻结 —— 要加新测量，就开一个新文件、新目录，而不是往旧文件里追加。这次用到的两个日志，SHA-256 分别在 `38e67630…` 和 `17f36f75…`，从头到尾一个字节都没变过。

**请求的模型和实际解析的模型都要记。** 我调用时写的是别名 `jev-latest`，但 42 条记录的实际返回值都是 `jev-1.13.0`。别名是会漂移的，只有响应能说明到底是谁回答了。所以两个字段都记下来。

**不是自己算的东西就标出来。** token 数用的是 API 返回的 `usage` 值，从不估算。成本和延迟是本地推导，就明确标成本地推导，而不是当成测量结果。

**派生产物不能漂移。** `results/` 下面除了两个 canonical 日志之外的所有文件，都是从日志重新生成的。CI 会重新生成一遍再和已提交的版本比对，不一致就直接失败。一个派生的报告永远不能变成第二个「真相来源」。

**先预注册，再调用。** 这是最重要的一条，第 8 节会专门讲。

做到后面我意识到，这个仓库真正想评估的其实不只是 Jev。**它同时也在评估我自己有没有资格从一次模型输出推出更大的结论。** 而这个问题在大多数时候的答案都是：没有。

### 顺便说一下成本

这 54 次调用总共花的钱，按本地估算约 **0.001 美元** —— 没错，是千分之一美元这个量级。这个数字是**本地估算**，不是账单 —— TypeSafe Console 的计费才是权威。写在这里只是为了说明：独立验证一个模型行为，门槛比很多人想象的低。

## 4. 第一轮实验到底测了什么

第一轮登记了 10 个实验，全部执行完毕，一共产生 **42 条核心记录**。事后我把它们按目的聚成四类，因为这比按时间顺序罗列更能说明它们在测什么：

| 主题 | 实验 | 在测什么 |
|---|---|---|
| **输出语义** | `01_primitives`、`02_structured_addressing`、`06_composite_scoring` | 三种原语的返回形状；结构化 state 的寻址；多个原子 Score 在 Python 侧合成为一个风险值（权重在运行前冻结） |
| **工作流经济性** | `03_parallel_questions`、`05_speculative_fanout` | 共享 state 的问题批处理到一次请求 vs 拆成多次；一次请求里带上两个分支的后续问题 vs 等第一个答案回来再发第二次 |
| **决策行为** | `04_confidence`、`07_instruction_precision` | confidence 作为代码侧 gate 的输入；模糊 vs 明确的决策边界 |
| **重复性与控制** | `13_repeatability`、`13b_ambiguous_repeatability`、`12_function_routing` | 逐字节相同的请求重复发送；路由到冻结的注册表里的函数名和参数 |

需要说明的是，`04_confidence` 只有 **2** 个用例，`12_function_routing` 只有 **4** 次调用。这些数字小到不能支撑任何比率，只能支撑「在这几个合成用例上，事情是这样的」。

**这 10 个实验都没有留下一条既相对于 TypeSafe 公开材料是新的、又被我自己的数据支持的结论** —— 也就是冻结文档所说的 `NO_STRONG_JEV_SPECIFIC_NOVEL_FINDING_YET`。下面分三类说。

## 5. 我复现了什么

有一件事本地测出来很干净：**把共享同一个 state 的多个问题放进一次请求，输入 token 会明显下降。**

具体地，`03_parallel_questions` 把五个问题针对同一个 state 放在**一次**请求里，两轮顺序平衡的循环合计消耗 **816** 输入 token；把同样五个问题拆成**五次独立**请求，同样的两轮合计消耗 **3,480** 输入 token。

由这两个数可以直接算出：**4.2647×** 的输入比，即 **76.55%** 的节省，而且两个臂之间 **10 / 10** 个选中值完全一致，最大绝对差为 **0.0**。

这个效应是真实的，而且很大。但它的边界必须一起说：

- 这是**一份 payload** 上的数字，五个问题全部读同一个 state —— 而这恰恰是这个节省所依赖的条件。
- 它是**两个顺序平衡循环、一次会话**内的测量，不是平均值，更不是分布。
- 它**不是**一个通用的批处理倍率，也**不能**和厂商公布的倍率放在一起比较。TypeSafe 在 `primitives.md` 里写的是「13 个问题 batch 到一次调用，比 13 次分别调用便宜 11.5×、快 9.6×」，而在并行问题那一页写的是「12.2× cheaper and 10.0× faster」。**这是两种不同的 workload —— 问题数不同、payload 不同、分母不同、会话不同。** 把「官方 12.2×」和「本地 4.26×」并排写成「官方 vs. 实际」是范畴错误。

诚实的说法只有一句：**在这个 payload 上，本地测量复现了官方描述的共享 state 摊销机制。**

而且这个机制是**预期之中**的。公开的第三方测量在同一模式上走得更远 —— 它们变化了 batch size，还给出了准确率随 batch size 变化的曲线；我这个实验从头到尾只用了固定的一份 payload，没有变化过任何 batch 参数。

所以这条属于「独立复现」，不属于「发现」。

## 6. 那些看起来有趣、最后被我删掉的东西

这是整篇文章里我最想写的一节。

第一轮跑完之后，手上有七个看起来可以写一写的候选项。我逐个做了对抗性审查，问的是同一个问题：**这件事既相对于 TypeSafe 公开材料是新的、又被我自己的数据支持吗？**

七个全部没有通过。其中两个我分享一下，因为它们的故事性最强 —— 也正因为最强，才最需要认真删掉。

### 稳定标签 ≠ 稳定分布

我把一份逐字节相同的 512-token 请求发了五次。**胜出的 Choice 标签 5 / 5 都没有变。** 但在那个稳定的标签底下，分布是在动的：前二名间距最多移动了 **0.07**，`Score` 落在 **1.58–1.63**，`confidence` 在 **0.24–0.30** 之间，还有一次出现了前两名之间的**精确并列**。

这个观察我当时觉得挺有意思。然后我在官方 cookbook 里找到了它：TypeSafe 自己的文档报告了 8 个问题里有 2 个出现标签翻转，以及一个非零的、逐标签的概率标准差（均值 0.0098，单标签最大 0.0515），并且明确写了「当两个标签接近时，很小的变化仍然可以翻转 top label」。

也就是说，**「标签稳定但分布在动」这件事，被官方的两个事实直接蕴含了。** 厂商没有用我这句措辞，但那句话不是我观察到的那个东西。

更决定性的是公开材料。有一份公开的 chaos test 报告说，他们把**逐字节完全相同的请求**发给 Jev 五次，得到的是 `0.03, 0.03, 0.03, 0.04, 0.04`，并且在约 1,490 次捕获调用上测了 jitter floor。也就是说，我以为是「我们独有」的那个设计 —— 用逐字节相同的请求做重复 —— **别人已经做过，样本量比我大，统计比我好。**

结论：**有意思的观察 ≠ 新的发现。** 这两件事之间隔着的，恰恰是「有没有人先做过」。

### 那个「越过了 0.60 门槛」的模糊用例

另一个候选来自 `04_confidence`：一个我特意设计成模糊的用例，返回的 intent 是 `other`，confidence 是 **0.61**，正好越过我在代码里设的 0.60 门槛，于是被判定为 `accept`。

这个故事听起来像是「模型在一个很微妙的边界上做了判断」。但它不是。

`0.60` 是**我自己在 `experiments.py` 里写下的常量**，而且我在代码注释里就标了它是 demonstration threshold —— 没有校准过、没有在任何数据上调过、不声称最优。TypeSafe 的文档自己也在两个不同的页面上对同一个示例用了 0.5 和 0.6 两个不同的门槛，并明确说门槛必须按领域调。

而且这次返回的分布根本不接近：**0.74 vs 0.26，间距 0.48。** 那个「模糊」是我 state 设计的属性，不是返回分布的属性。官方的 k=3 近似式 `(3 × 0.74 − 1) / 2` 把 0.61 **精确地**重算了出来 —— 它就是一个算术结果。

所以：**`0.61 ≥ 0.60` 是我们自己的策略算术，不是 Jev 模型的发现。** 移动那个常量，结论就会变，而且一次模型调用都不需要发生。

### 还有一条，关于「模型拒绝执行」

`12_function_routing` 里，我让模型把请求路由到一个事先冻结的函数注册表。结果是：模型**4 / 4** 次匹配上了预期的函数，**4 / 4** 次匹配上了预期的参数 —— 然后**4 / 4** 次全部被我的策略拦下来送到 `human_review`，handler 一次都没有进入。

这个结果很容易写成「模型不敢执行」。但四个拦截全部可以追溯到我自己在 `routing.py` 里写的常量：路由置信度分别是 0.76 / 0.58 / 0.72 / 1.0，而我把 floor 设在了 0.8 —— 前三个只是因为落在这条线下面才被拦；第四个置信度是 1.0，是被 `needs_human_review` 的 0.94 相对 0.5 的门槛拦下的。文件里紧挨着常量写着一行注释：*nothing in the docs says 0.8 is the right line*。

诚实的那句话是：**router 是在按我的指令拒绝执行，不是 Jev 产出了不可用的 confidence。**

**这一节的重点是：最容易写进博客的故事，恰恰是最需要被删掉的。** 七个候选里，效应最大的两个（这一节的第一个，和第 5 节的 4.26×）是死得最彻底的，而且两次都是**别人已经公开做过**这件事决定了它们的命运，不是我的数据不够好。

没有任何一个候选因为「不好看」被杀掉，也没有任何一个因为「好看」被留下来。

## 7. 唯一值得追的一条线

七个候选里只有一个活了下来，而且它活下来的理由不是效应大，恰恰是**它有一个明确的、可以证伪的未知**。

事情来自 `07_instruction_precision`。我在一个**逐字节相同的 82 字节 state** 上，改了决策边界的写法：模糊的边界下，一个 `Noul` 返回 **0.75**；明确的边界下，返回 **0.20**。在同一个 state 字节上，0–1 概率上的差异是 **0.55**。

这个效应很大。但它有两个问题：

**第一，0.75 和 0.20 都不是 ground truth。** 两个臂都无所谓「正确」，它们只是两个不同的数。

**第二，也是关键的那个 —— 我的两个臂是同时改了 `instructions` 和 `criteria` 的。**

所以这个实验**不能**支撑任何一句这样的话：

- ✗「Jev 更看重 criteria。」
- ✗「光改 prompt 措辞就造成了 0.55。」
- ✓ 能说的只有：「在这份 payload 上，两个字段一起从模糊改到明确，`Noul` 移动了 0.55。」

而这件事恰好撞上了一个官方文档没有回答的问题。TypeSafe 的已知局限页把「字面阅读」列为失效模式第一条，给的补救办法是：在 `instructions` 里说明确的条件，把边界情况写进 `criteria`。**但它给的是一个打包的建议，从来没有拆开过。** 官方还说了一句「把 criteria 当作 instructions 的延伸」。

问题就在这里：**那个边界，到底是 `instructions` 在承载，还是 `criteria` 在承载？**

官方没拆。我自己的数据没拆（两个字段一起改的）。公开材料里我也没找到有控制变量的归因实验。于是这成了唯一一个通过了审查、又值得花几个调用去问的问题。

顺便说一句，这个问题的公开新颖性检查返回的是 `PUBLIC_NOVELTY_UNRESOLVED` —— 我把它记成「未解决」，而不是「没有人做过」。这两者不是一回事。

## 8. P3：一次真正的预注册实验

在发第一个请求之前，我把设计、顺序、统计方法和每一条阈值全部写下来并提交了。这是这个项目里我认为最值得保留的习惯。

设计是一个 2×2，把两个字段交叉开：

| 臂 | instructions | criteria |
|---|---|---|
| `N` | 模糊 | 模糊 |
| `I` | 明确 | 模糊 |
| `C` | 模糊 | 明确 |
| `B` | 明确 | 明确 |

每个臂重复 **3** 次，一共 **12** 次调用 —— 这是一个写死在预注册里的硬上限，不允许重试循环、不允许轮询、不允许「再补几次看看」。

固定顺序是 `N1 → I1 → C1 → B1 → B2 → C2 → I2 → N2 → C3 → N3 → B3 → I3`，两端和中间都做了平衡。

预注册里还写了一条**设计风险**，我觉得它比阈值本身更重要：`I` 和 `C` 两个臂必须陈述**同一个**边界，只在「写在哪里」上不同。如果哪个臂让 instructions 和 criteria 互相矛盾，它就触发了官方记录的另一条失效模式（「矛盾的 instructions 和 criteria」），那个臂就是协议违规，不是数据点。

最后，`N` 和 `B` 这两个端点臂，是原来 `07` 实验两个臂的三次重复版本。它们的作用是**诊断** —— 检查原来的效应这次还在不在。它们和所有阈值一样，在第一个请求发出之前就冻结了，所以事后没有人能拿它们去调阈值。

GO 和 KILL 条件也是预先写死的。其中决定性的那条是：

```
K1:  |I_med − C_med| < 0.1   →  归因失败
```

## 9. P3 的原始结果

12 次调用全部成功。原始值全部列出 —— 中位数是对它们的概括，不是它们的替代品：

| 臂 | Noul 原始值 | 中位数 | 极差 |
|---|---|---:|---:|
| `N`（都模糊） | 0.77, 0.76, 0.75 | 0.76 | 0.02 |
| `I`（只改 instructions） | 0.31, 0.33, 0.29 | **0.31** | 0.04 |
| `C`（只改 criteria） | 0.37, 0.36, 0.33 | **0.36** | 0.04 |
| `B`（都明确） | 0.20, 0.21, 0.20 | 0.20 | 0.01 |

端点的复现是成功的：原来 `07` 观察到的 0.75 → 0.20（移动 0.55），这次跑出来 `N` 中位数 **0.76**、`B` 中位数 **0.20**，间距 **0.56**，每个臂 3 次重复、同一份 payload。次序保住了，量级也保住了。

但真正发生的事情在两个单字段臂上：**它们都朝着明确基线移动了大部分距离。**

- `I` 中位数 0.31，比 `N` 的 0.76 低 0.45，相当于这次 0.56 端点间距的 **80.4%**。
- `C` 中位数 0.36，低 0.40，相当于 **71.4%**。
- 而两个单字段臂之间，只差 **0.05**。

**0.05 < 0.10，K1 触发。**

按照预注册的规则，这意味着：**在这个设计和样本量下，原来的效应无法被归因到 `instructions` 或 `criteria` 中的任何一个字段。**

最终判定：

```
P3_KILL_NO_SINGLE_FIELD_ATTRIBUTION
```

关于那两个百分比（80.4% 和 71.4%），必须说清楚：**它们是我对上面几个中位数做的描述性算术，不是决策规则的一部分。** 没有任何阈值是从它们推出来的，把它们完全忽略掉，判定结果一个字都不会变。

## 10. 为什么一个 null result 是好结果

这次 P3 得到的不是一个「没做出来」的结果，而是一个真实的负结果。

它**不是**实验失败。原来的大效应**被复现了** —— 0.55 那次移动，这次以 0.56 的间距重新出现，端点次序一致。失败的是**归因**：这个设计没法说清效应来自哪个字段。

这里有一条我认为比这次实验本身更重要的研究方法：

> **效应很大 ≠ 原因已确定。**

看到 0.55，最自然的冲动是马上去写「Jev 更看重 X」。但一个把两个变量一起改掉的实验，无论效应多大，都答不了这个问题。要回答它，你需要的不是更多的调用，而是一个**能把变量拆开**的设计 —— 而且这个设计必须在看到数据之前就定好，否则你会忍不住一直调整到它能说出你想听的话。

同样重要的是，**不能把 null result 偷偷翻译成一句更好听的话。** 比如：

- ✗「Jev 同时看重 instructions 和 criteria。」 —— 这个设计区分不了「两个字段都在起作用」和「混合具体度的构造物在起作用」，这是两回事。
- ✗「criteria 才是关键。」 —— 数据说的恰恰相反，如果非要说偏好，`I` 臂动得还更多一点。

还有两条限制是承重的，必须跟着结论一起走：

**`FIELD_ALIGNMENT_CAVEAT`**：交叉的两个臂，是「一个更宽的字段 + 一个更窄的字段」，不是两个独立变化的定义。所以这个结果说的是**这个混合具体度构造**的性质，不是 Jev 到底把决策边界「存在哪里」。

**n = 3**：三个重复能支撑一个中位数和一个极差，**支撑不了任何区间估计**。所以这里没有报告任何置信区间 —— 不是我不想报告，是这个设计支撑不了。

结论就是它字面的意思，一个字都没有多：**在这份 payload、这个样本量、这个设计下，效应无法归因到单一字段。**

## 11. 分析器有一个 bug，我把它写进了记录

P3 之后我发现分析器有一个缺陷，我把它完整地留在了仓库里。

具体是这样：在预注册里，GO-1 和 GO-2 是**两个独立的条件**。但我在分析器里把它们写成了一个合并的判断，结果是 `(GO-1 PASS, GO-2 FAIL)` 这一对**在代码里根本无法被表示**。而在这份数据上，预注册规则算出来的恰好就是这一对：两个单字段臂都越过了 GO-1 的线（`I_med = 0.31`、`C_med = 0.36`，线是 0.475），但没有任何一种指派能让对方留在 GO-2 的模糊基线带里。有缺陷的分析器把 GO-1 报成了 FAIL，还打印了一句和数据矛盾的话。

我做了这些事：

- **在有缺陷的分析器冻结点之后、测量被记录的那次提交里，就把缺陷披露了出来** —— 没有等别人发现。
- 缺陷修复是一次**独立的、后置的提交**。修复的时候**没有发出任何调用，也没有重跑任何一次调用**。12 条记录在修复前后逐字节相同。
- **没有改动任何阈值、任何规则。** 预注册文档和冻结时逐字节相同。
- 修复后的分析器**从没变过的日志重新渲染**了结果文档。

最关键的检查是这个：**原始分析器算出来的主判定，和修正后的完全一样。**

为什么？因为 GO-1 单独从来都不构成判定 —— 冻结的规则要求的是一条越过 GO-1 的臂**配上**一条落在 GO-2 带里的对应臂，而这份数据上根本不存在这样的配对。K1 在 GO 块之前就被求值，而且它触发了。所以这个缺陷弄错的是**推理过程的显示**，不是决定本身。

我想用这件事说明的是：

> **预注册不能保证代码没有 bug。但 provenance 能让 bug 的修复不污染测量历史。**

修复过程里没有任何一个数字被重新测量过，也没有任何一条记录被改写过。一个后来的人可以自己 `git show` 出修正前的那次渲染，看到缺陷、看到披露、看到修复，然后自己判断这一切是否成立。**这就是为什么那次错误的渲染被保留在 Git 历史里，而不是被抹掉。**

顺便说另一件事，因为它属于同一个类别。P1 审计里有一行写的是「42 / 42 个 Noul 答案不携带 `confidence` 字段」。独立复核的时候发现，正确的数字是 **45 / 45** —— 42 是**记录**数，而那句话说的是**答案**数，42 条记录里一共装了 119 个答案。

结论没有任何变化（每一个 Noul 答案确实都没有那个字段），但数字确实错了。我**没有去改 P1 的文本**，因为它是历史审计产物；改了它，读者就再也分不清它里面哪些数字被动过。正确的值记在[勘误表](../ERRATA.md)里，P1 原文保持原样。

## 12. 工程上真正值得带走的东西

把 54 次调用压一压，下面几条是我认为可以迁移到别的系统里的。

### 1. 类型化的模型输出不等于语义上的真

schema 校验通过 ≠ 答案正确。这个项目里有 42 / 42 条响应全部通过 schema 校验，但**这什么都不能说明** —— 没有 ground truth，没有对抗性输入，只有良性 payload 上的格式合规。这是支持「类型安全」主张最弱的一种证据。

### 2. Confidence 不应该被当成单样本的正确性 oracle

官方文档把 calibration 的作用域限定在**一组**预测上，并明确说 confidence「描述的是模型的答案，不保证答案正确」。

我本地有一个比规则更扎心的例子：在 `06_composite_scoring` 里，有一个维度在 0–3 的评分表上拿了 **1.62**，而它的 confidence 只有 **0.24**，这个维度却承载了那个 state **97.4%** 的合成风险。算术是对的，confidence 是低的，它们只是两个不同的问题。一个把「低 confidence」读成「答案错了」、把「高 confidence」读成「答案对了」的策略，读的是错的数字。

明确说明边界：**这个项目既没有验证、也没有证伪 Jev 的 calibration。** `04_confidence` 只有两个用例，没有可靠性图，没有 ECE，没有 Brier score，没有独立的 ground-truth 数据集。任何方向都不行。

### 3. 语义路由和执行授权应该分层

这是我觉得这个项目产出的最有用的一条模式，而它来自一次**与设计预期相反**的运行。

模型的工作做得很好：4 / 4 匹配正确的函数，4 / 4 匹配正确的参数。然后 Python 侧的策略把每一条都拦了下来，handler 一次都没进入。

系统该怎么写：**模型回答「这个 state 是什么意思」，代码回答「我们被允许行动吗」。** 一个把「模型很自信地选了某个路由」直接当成「可以执行」的系统，恰恰移除了产生这次结果的那一层。

明确说明边界：那 **4 / 4** 是**合成用例上的计数，不是准确率**。而且每一个 handler 都是惰性的 —— 没有写文件、没有发消息、没有产生任何真实副作用。**在真实答案下，一条被允许的路由是否真的会走到 handler，这个项目从未观察到**（`ACTUAL_HANDLER_EXECUTION_UNTESTED`）。这个限制是写下来的，不是含糊过去的。

### 4. 批处理的经济性是 workload-dependent

只有当问题**共享同一份 state** 时，摊薄才明显。我的 4.2647× 属于一份特定 payload，不是 Jev 的属性，也不是一个通用倍率。

顺便说一个反直觉的会计问题。在 `05_speculative_fanout` 里，一次请求带上两个分支的后续问题，结果是 12 个推测性答案里有 4 个没被用上，看起来像浪费。但这笔账要按这个产品的价格表来算：**Jev 对输入 token 计费、对输出 token 定价为零**，而那些没用上的答案是输出 token。同时，**唯一计费的那一侧（输入）反而低了 400 token。** 所以「没消费却付了钱」这句话在这个产品上没有成本内容 —— 定价框架在一个方向上看着很有道理，在另一个方向上直接反转了。

### 5. 保留分布，不要只保留标签

在逐字节相同的请求下，标签 5 / 5 都没变，但标签底下的分布一直在动。如果只记录「选了哪个」，你会完全看不到这件事。

再说一次边界：**这个现象不是我们的发现**，它被官方文档蕴含，也被公开材料用更大的数据量复现过。这里值得记的只有一条实践建议。

### 6. 评估基础设施本身也需要被审计

这是这个项目最值钱的部分：canonical logs、从日志重新生成的派生产物、离线测试、勘误表、哈希、冻结。**所有这些都是为了让「哪些数字被动过」这个问题有一个机械的答案**，而不是靠作者的信誉。

一个具体例子：日志里有一个 `retry_count` 字段，它**永远是 `null`**。原因是 SDK 把重试次数写在被重试的**请求**上，而记录器读的是**响应**。所以 `null` 的意思是「没有被报告」，**绝不**是「没有发生重试」。这个字段没有被回填，也没有人拿它做推理 —— 它还留在那里只是为了让旧的行仍然可读。真正有效的是 `transport_attempt_count`，一个本地计数的出站 HTTP 尝试次数；它也只能支撑一句话：*这次调用没有被观察到重试*，**不能**支撑「这是纯粹的模型推理延迟」。

## 13. 五个已经删掉的实验

在公开发布之前，我把 **5 个已经登记但从未运行**的实验全部退休了，而不是为了「完整性」把它们跑完。

它们当初都是认真设计的，退休是因为站不住。举两个代表性的：

**`10_state_length`** —— 用不断增长的无关填充文本，装载一份固定的核心证据。三个缺陷叠在一起：没有独立的 ground truth（「正确」答案是我自己对一份我自己写的合成 bug 报告的读法）；每个长度档只有 **1** 次调用，split 不开 context rot 和随机波动 —— 而我自己另一个实验已经证明，逐字节相同的 payload 上 `Noul` 都会动；而且那些「填充段落」其实只有五句话在按 `index % 5` 循环，「中等」和「更长」两档的区别是同样的五句话重复了几遍，**不是无关内容累积了多少**。重复和累积是两种不同的操纵，所以这两档根本没有在变化这个实验名称所指的那个变量。

**`11_language_pair`** —— 英文和中文的等价输入。这个退休理由最值得看，因为**留下来**的诱惑最大：我本人和相当一部分读者是中文使用者，一个中英对照的结果会很好看。

但它有四个独立的问题：两个臂在语义上并不等价（英文 state 说客户想撤销重复扣款，配对的问题却问的是要不要退款 —— 这是两个不同的诉求）；语言和措辞被完全混淆（每种语言只有一种写法，所以任何差异都是「语言 × 措辞」）；每个臂只有 **1** 次调用；而且官方文档已经回答了产品层面的问题 —— 它直接写明英语是主要训练语言，其他语言包括 CJK 可以接受但**目前准确率较低**。

最后一条本身就是这个项目的规则在起作用：**「这个结果会很受欢迎」是关于读者论证，不是关于设计的论证。** 一个被混淆的、统计功效不足的、语义还有歧义的设计，不会因为它面向的读者是谁而变得可用。

**不运行一个坏实验，通常比得到一个无法解释的数字要好。** 退休一个从未运行的设计不会损失任何证据 —— 一个从未运行的设计只是一个意图，而删掉一个意图不是丢掉一个结果。

（顺带一提，这也是为什么这个仓库没有「登记但未运行」这个状态。要么跑，要么退休。）

## 14. 这些实验没有证明什么

每一个「我们能说什么」都应该配一个「我们没说什么」。下面这些是这个项目**明确无法建立**的，而且不是「以后再补」，是证据结构上不支持：

- **没有任何通用准确率。** 这个测量台里没有任何地方存在 ground truth。「4 / 4」是**合成用例上的计数，永远不是比率**。
- **没有验证或证伪 calibration，任何方向都没有。** 见第 12 节。
- **没有模型延迟 benchmark，也没有任何加速结论。** 延迟被记录了，但它是包着一整段东西的墙钟：DNS、TCP、TLS、连接池状态、服务端排队、上游负载、本地调度。没有任何一个臂被称作「更快」。
- **没有通用的批处理倍率。** 4.2647× 是一份 payload 的属性。
- **没有确定性结论 —— 两个方向都没有。** 逐字节相同的请求返回了不同形状的分布，但那只是两个 payload 上的少数几次重复，不足以成为判定；而且我读到的官方材料里，没有任何一处对确定性做出过任何方向的声明。
- **没有广义的 hallucination benchmark。** 这里唯一测量的轴是**良性 payload 上的 schema 合规**，没有做任何对抗性尝试。
- **没有生产安全认证。** 每一个 handler 都是惰性的，没有写文件、没有发消息、没有产生任何真实副作用。
- **没有关于 instructions 和 criteria 谁更重要的通用结论。** 一份 payload、每个臂 n = 3、而且是 null。
- **没有 NAS 适用性结论。**

再补两条不叫 marker 但同样有约束力的：

**不做厂商主张的仲裁。** 当官方数字和本地数字不一样时，这个仓库说的是「它们不可通约」，而不是「官方其实是错的」或者「本地其实证明了官方」。厂商数字是关于他们 workload 的主张。

**合成数据的边界。** 全部 state 都是合成的。这个仓库里没有真实的个人数据、客户数据或专有数据。

## 15. NAS 只是一个未来的问题

我确实计划在将来评估 Jev 是否适合 NAS 这类工作负载。但这篇文章里的任何东西都**不能**用来支持那个方向：这里没有 NAS 实验、没有 NAS 数据集、没有任何 NAS 测量，而被退休的五个设计里，有可能触及搜索相关行为的那些也从未运行。

所以正确的说法只有一个：**下一步如果要研究 Jev 适不适合 NAS，需要从 NAS 的任务结构出发重新验证**，而不是因为已经研究过 Jev，就反过来去找应用场景。**不能因为手上有锤子，就把问题看成钉子。**

## 16. 结语

回到最开始那个问题：如果模型返回的是带类型的概率答案，而不是文本，Agent 会变成什么样？

这 54 次调用没有回答它。它们做到的是一些更小、更靠前的事情：把「我认为 Jev 是这样的」换成了一条条可以被别人检查的记录 —— 包括那两个看起来很漂亮、最后因为有前人做过而被删掉的效应，包括那次把两个变量一起改掉、因而无法归因的 0.55，包括一次诚实的预注册负结果，也包括一个被我完整留在 Git 历史里的分析器 bug。

发布的时候，这个仓库的诚实总结是这样一行状态：

```
NO_STRONG_JEV_SPECIFIC_NOVEL_FINDING_YET
```

**这份仓库里没有一条既相对于 TypeSafe 公开材料是新的、又被我自己的数据支持的 Jev 发现。** 每一个本地大效应，要么是在复述一个官方已经记录的行为，要么是我自己 Python 侧策略的产物。

我认为这是个好结果。一个用来检验发现的仓库收到了否定的检验结果，说明它在做它该做的事 —— 而不是在累积战利品。

如果你要对这个仓库说点什么，[`BLOG_CLAIM_CONTRACT.md`](../evidence/v0.1.0/BLOG_CLAIM_CONTRACT.md) 把它所允许的说法分成了三类（可以平铺直叙的、必须带 scope 的、任何情况下都不能说的）。**如果你抓到这篇文章里有哪句越过了它，那不是措辞问题，那是这个仓库不再值得被引用的开始。**
