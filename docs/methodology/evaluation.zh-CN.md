# 方法论

[English](evaluation.md) | **简体中文**

本实验台如何决定自己「有资格说什么」。下面的规则不是风格偏好 —— 它们就是本仓库中一个数字之所以具有
特定含义的原因。

---

## 1. 声明标注

派生报告中的每一句断言都携带以下五种标注之一：

| 标注 | 含义 |
|---|---|
| **OFFICIAL** | TypeSafe 关于*他们*工作负载的说法。不是关于本机器的证据。 |
| **DESIGN ASSUMPTION** | 本仓库做出的选择，不是关于模型的事实。 |
| **LOCAL MEASUREMENT** | 由本仓库中的一次运行产生，且存在于某份权威日志中。 |
| **DERIVED CALCULATION** | 在本地对测量值做的算术（延迟、成本、比值）。 |
| **LIMITATION** | 关于这份证据能支持什么的明确边界。 |

P1 审计使用了一套更细的词汇来描述官方说法与本地证据之间的关系，因为「确认 / 未确认」对它来说过于粗糙：

```
DR  DIRECT_LOCAL_REPRODUCTION      DS  DIRECTIONAL_LOCAL_SUPPORT
LE  LOCAL_EXTENSION                AT  APPARENT_TENSION
NT  NOT_LOCALLY_TESTED             ND  NOT_TESTABLE_WITH_CURRENT_DESIGN
NO  NOT_AN_OFFICIAL_CLAIM
```

其中 `ND` 是最需要留意的。当本地记录与某项主张在**两个方向上都不具可比性**时，就会用到它 —— 既不是
反驳，也不是确认。厂商 70–500 ms 的延迟区间就落在那里：本实验台的时间窗包含 DNS、TCP、TLS 建立、连接
池状态、服务端排队、上游负载与本地调度，因此这两个数字不是同一个量。

### 分离规则

> 官方说法绝不会被改写成「本仓库测量到的东西」。

最清楚的例子：TypeSafe 公布了他们 cookbook workload 的批处理倍率。本实验台在另一份 payload 上测到了
**4.26×**。这两个数字绝不能并排写成「官方 vs. 实际」—— 不同的 workload、不同的 payload、不同的分母、
不同的会话。它们被记为一则主张与一项测量，各自待在自己的类别里。

## 2. 实验设计规则

- 所有 state 都是**合成的**。绝不包含真实个人、客户或专有数据。
- 每个实验都在开始前声明**固定的 case 列表**，因此一次运行的成本在开始前就是可知的。如果一个实验需要
  循环，它就必须改为带有一个有文档记录的常数上限。
- 一次真实 API 调用恰好产生**一条记录**，由 `UsageRecorder` 写入，无论成功还是抛异常。没有任何路径
  绕过 recorder。
- **绝不估算 token。** Token 计数是 API 返回的 `usage` 值。
- 同时记录 `model_requested` 与 `model_resolved`。别名会移动；只有响应能说明是哪个模型回答的。
- 代码做算术，Jev 做语义判断。绝不让 Jev 去计数、求和、比较数字、在得分档位之间插值，或计算日期差。
  当某个实验*确实*要探测一个有文档记录的数值限制时，正确的代码侧答案会被放在它旁边。
- 在合并之前，**在代码中**归一化得分量表（`score / (levels - 1)`）。

### 预算

`run` 默认硬上限 **8** 次 API 调用。`run-all` 在 `--max-requests` 未覆盖该档时**拒绝启动** —— 批量运行
必须是明确的人类决定，绝不能是意外。认证失败会立即中止运行，而不是把剩余预算花掉。失败的 case 会记录
错误并继续，因此部分结果仍然带有溯源信息。

### 唯一带控制流的实验

`05_speculative_fanout` 会让下一个请求依赖于上一个答案，因此它声明的 4 个 case 可能变成 6 次调用。它
显式声明了该上限（`call_ceiling`），预算检查用的是这个上限，永远不是 case 数。它的分支规则在运行前已
冻结：一个未指名任何已知分支的主答案会发送**零**次后续请求，因为对于运行期才选出的分支来说，不存在
经过离线审计的 payload。

## 3. A/B 实验能说明与不能说明什么

这里的 A/B 所变化的东西比它的名字暗示的更多，而这个差别在阅读结果时很重要。

### `03_parallel_questions` —— 批量 vs. 分开

两个**顺序对称**的循环：先批量后分开，再先分开后批量。这个实验的第一个版本把批量臂固定在每次运行的第一
位，使臂身份与请求位置被完全混淆 —— 这正是现在每条记录上都有那四个位置字段的原因。

Token 与成本的比较是紧的：相同的 state、相同的问题定义，一次请求携带全部五个问题，对比五次请求各携带
一个。**延迟仍然只是观察性的。** 两个循环平衡了顺序，但远远不足以声称加速，而这个实验从不声称加速。
批量臂自己的两次观测相差 **2592.9 ms**，而臂间均值差是 **1327.2 ms** —— 臂内离散度超过了臂间差异。

### `02_structured_addressing` —— 结构化 vs. 散文

**不是干净因果检验。** 有三件事同时变化：state 的表示形式、问题能否指名字段路径，以及 payload 长度
（结构化臂更长）。因此 token、延迟与成本差异**被长度混淆**，只作为观察报告，绝不归因到表示形式。
`state_chars` / `state_utf8_bytes` 按 case 记录，以便这个差距始终可测。

### `04_confidence` —— 具体 vs. 模糊

两个臂都留在同一个场景中，实体相同、长度相近、`Choice` 与 `Score` 的 criteria 完全一致，因此主要变量
就是证据的具体程度。**正确性与 confidence 分开报告**：清晰臂声明了预期标签，模糊臂不声明，而不是编造
一个，因此「自信地答错」保持可见。`Score` 的 confidence **不是**正确性，不能与 `Choice` 的 confidence
相比。

### `07_instruction_precision` —— 模糊 vs. 明确

state 被保持**逐字节相同**，且两个臂**都**含有 criteria，因此答案空间相同。它变化的是决策边界被表述
得有多明确，而且是同时改 instructions 与 criteria —— 它**不**把指令措辞与 criteria 措辞隔离开。明确的
criteria 刻意避开了 state 自身的名词，因此正确答案不可能来自词面匹配。`Noul` 没有分布也没有 confidence，
所以这个实验只比较 `Noul` 标量、token、延迟与成本。

### `05_speculative_fanout` —— fan-out vs. staged

Fan-out 为自己可能用不上的答案付费；staged 为第二次往返付费。这里的浪费以**问题数**计，绝不按 token
计，而且两个臂在请求数与发送的问题总数上都不同 —— 所以这个比较是一种权衡，不是排名。没有把任何臂称为
更快：两组配对在延迟方向上并不一致。

## 4. 关于阈值

`04_confidence` 依据答案自身的 confidence 在代码中路由 —— `confidence < 0.60` 升级，达到或高于它的
接受。`12_function_routing` 使用一条 0.8 的路由下限和一条 0.5 的复核线。

**其中每一个都是演示参数。** 未经调优、未经校准、也未声称最优。TypeSafe 文档本身在同一个示例上，一个
模式页面用 0.6、另一个用 0.5，并明确指出阈值取决于你的领域、必须在你自己的数据上调优。本地数字与某份
文档示例的巧合**不构成佐证**。

每个门控的决定，以及把它标注为演示参数的依据字符串，都会写进记录的 `notes.derived`，因此路由在事后是
可审计的。这里没有任何内容声称某个阈值是最优的，而通过门控**并不**证明底层答案是正确的。

## 5. 延迟政策

这里的延迟是**围绕单次 SDK 调用的墙钟时间**，而它继承了一个底层环境：新建客户端会付出它的同批调用不必
付出的 DNS、TCP 与 TLS 成本。因此，在两个臂之间比较时序差异，在顺序被控制之前不构成关于模型的证据。

1. **永远平衡顺序。** 任何一个臂都不允许在每次运行中都处于同一位置。这是唯一不可妥协的一条，而那四个
   位置字段存在的意义就是事后核验它。
2. **把首请求单独报告；不要悄悄丢弃。** 权威日志保留每一次调用。任何排除预热观测的派生视图都会明确说明，
   并展示它排除了什么。
3. **不要为了省几次调用而放弃重复。** 多两次调用只花几分钱的一小部分；一个不平衡的比较一文不值。
4. **在读任何延迟之前先看尝试次数。** `transport_attempt_count` 只授权一句结论：*本次调用未被观察到
   发起超过一次 HTTP 尝试。*
5. **绝不把 `attempts == 1` 等同于纯模型推理延迟。** 单次尝试里仍然包含 DNS、TCP、TLS、连接池状态、
   服务端排队、上游模型时间与本地调度。这个计数排除的是*被观察到*的 HTTP 重试，除此之外什么也不排除。

即使顺序是平衡的，结论也是**观察到的延迟比较**，并且必须如此命名。

### 为什么 `retry_count` 是死字段

SDK 把 `X-TypeSafe-Retry-Count` 设在被重试的*请求*上；recorder 读的是*响应*上的这个 header，而服务端
不会回显它。因此它永远是 `null`。它被保留只是为了让旧行仍然可读，从不回填，其中的 `null` **绝不**意味
「没有发生重试」。实际有效的字段是 `transport_attempt_count` 与 `transport_retry_count_observed`，由
本进程中的一个请求事件钩子统计 —— 它只把一个整数加一，不检查任何东西：不读 header、不读 URL、不读 body。
它不可能泄露凭据，因为它从不看凭据。

前后差值假设实验**串行**运行，CLI 确实如此。引入并发将需要重新审计这一点。

## 6. 如何读日志

`results/usage.jsonl` 是测量本身。`results/` 下的其他每个文件都是基于它重建的视图。

- **`notes`** 携带 case 的设计元数据（属于哪个臂、存在预期标签时包含预期标签），以及 `notes.derived`
  —— 由答案在本地计算出的值，例如 confidence 门控的路由决定。派生值不额外消耗 API 调用。
- **字段缺失意味着「未记录」**，绝不意味着零。schema-1 的行缺少位置字段；早于探针的记录没有
  `attempt_count`。
- **Null 意味着「未报告」**，绝不意味着「什么都没发生」。
- **`results/` 是有选择地提交的。** 两份权威日志与最终报告被纳入版本控制；其他所有派生文件都被忽略，
  因此克隆得到的是测量数据，视图则重建。

### 七条基本规则

1. 官方 TypeSafe 文档是产品语义的唯一权威。
2. 官方说法与本地测量分开记录，每个结果都会说明自己属于哪一类。
3. 代码做算术，Jev 做语义判断。
4. 优先对共享同一 state 的问题做批处理。
5. 始终记录实际解析的模型与 API 返回的精确 `usage`。
6. 本仓库中永远没有密钥。
7. 所有 state 都是合成的。
